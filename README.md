# token-miser

给 AI agent 的省钱技能：输出 token 要花钱，这套规则让模型少说废话、少绕弯、多复用已读内容。

用户规则来自实盘调优，包含三条核心洞见：

1. **输入比输出便宜十几倍** —— 多读文件验证，少自言自语；思路优先从已读内容里找，别一有问题就搜网。
2. **突破进展三问** —— 有了"妙招"先别顺着推：找更简洁的方法 → 成功就重复，失败才沿用。防自嗨式局部最优。
3. **禁止废话税** —— 不总结刚做过的事、不客套、不复述需求，代码能表达就用代码。

## 安装

方式 A：常驻（每个会话自动生效，推荐）

把 `AGENTS.md` 内容放到 agent 的全局指令文件（如 Claude Code / dsh 的 `~/.dsh/AGENTS.md` 或项目根 `AGENTS.md`）。

方式 B：按需技能

把 `SKILL.md` 放进 skills 目录（如 `~/.dsh/skills/token-miser/SKILL.md`），说"少废话 / 省着点"触发。

## 实测数据

两个难度相近的任务，同一模型/环境，各跑一次（n=1，仅供参考）：

| 维度 | 有 Skill | 无 Skill | 变化 |
| --- | ---: | ---: | --- |
| 轮次 / 步数 | 5 轮 / 42 步 | 4 轮 / 40 步 | 相近 |
| LLM 耗时 | 3 分 48 秒 | 20 分 44 秒 | **-81.7%** |
| 工具耗时 | 21 分 27 秒 | 12 分 44 秒 | +68% |
| 总墙钟 | 25 分 15 秒 | 33 分 28 秒 | -24.6% |
| 首 token 延迟 | 1.3s | 1.4s | 相近 |
| 生成速度 | 89 tok/s | 77 tok/s | 波动，勿过度解读 |
| 缓存命中率 | 97% | 98% | 相近 |
| 输入令牌 | 2.5M | 3.7M | -32.4% |
| 输出令牌 | 15.5K | 91.8K | **-83.1%** |

诚实解读：

- 输出是主要成本（贵），省 83%；输入基本全走缓存（便宜），再省 32%。
- LLM 思考时间省 81.7%：少自问自答、少绕弯，token 少了，思考也短了。
- 有 Skill 时工具耗时反而更长——少说多做的代价是更多次实操验证（读写文件代替自言自语）。按"输入便宜、输出贵"的原则，这笔交易划算。
- 生成速度 89 vs 77 tok/s 与输出长短无关，属服务端波动，不作为卖点。
- n=1 样本，数据仅证明方向，不保证幅度。

### 输出/输入比趋势（随项目规模反向下降）

| 输入量 | 输出/输入 |
| ---: | ---: |
| 20.5M | 0.438% |
| 44M | 0.3% |
| 63.7M | 0.237% |
| 80.4M | 0.219% |
| 117M | 0.269% |

项目越大废话率越低：越熟悉代码库，越不需要文字解释"我在读什么"。输入靠 99% 缓存近零成本，输出被压死在天花板下，不随输入膨胀。注意 117M 的 0.269% 略高于 80.4M 的 0.219%——降到 0.22%~0.27% 后进入**平台区**，非严格单调；但相对冷启动小任务（763K 输入 → 10K 输出 1.31%；668K → 6.3K 0.94%）仍有 4~6 倍差距。

### 单步成本趋势

| 会话 | 输入 | 步数 | 费用 | 单步成本 |
| --- | ---: | ---: | ---: | ---: |
| 凌晨（无 Skill） | 25.5M | 68 | ¥7.96 | ¥0.117 |
| 16 轮（有 Skill） | 32.6M | 204 | ≈¥10.5 | ¥0.051 |
| 20 轮（有 Skill） | 44M | 242 | ≈¥12.3 | ¥0.051 |
| 超大上下文（有 Skill） | 63.7M | 299 | ≈¥11 | ¥0.037 |

输入 +150%（25.5M→63.7M），单步成本 -68%。规模越大单位成本越低——缓存吃掉了增量输入，规则压死了增量输出。

对照未装时段（25.5M 输入 / 152K 输出，0.596%）：输出占比被持续压到 0.5% 以下，步频从未装的 3.2 步/分提到 5.3 步/分（+65%）——少生成 = 串行生成时间短 = 更快进入下一步工具调用。**省 token 与提速是同一件事的两面。**

### 同 Bug 对照：有 Skill vs 无 Skill（备份 harness A/B）

同一个 bug（插件缺 `inject` 声明），两种模式的处理：

| | 有 Skill | 无 Skill（备份环境） |
| --- | --- | --- |
| 第一反应 | 报错 → 读源码 | 报错 → 怀疑"我之前读的版本对不对" |
| 精力花在 | API 入参结构（逻辑层） | 硬链接 inode、路径真假（元数据层） |
| 结论前输出 | < 500 tokens | 2000+ tokens 内心戏（Wait/Actually/Let me recall） |
| 决策路径 | 线性：读代码 → 改 → 验证 | 树状：自我怀疑 → 预支"未来可能的报错" → 犹豫（最终也 boot，只是绕路） |

### 账单拉平后的诚实结论

两个时段缓存率都 >95%，输入成本两边都接近免费，差价全在输出。但**任务不同、模型不同结论也不同**：

- DeepSeek 本身话痨程度低，按任务量拉平后，Skill 的边际收益 ≈ **17.7%**（下限；任务性质差异使真实值可能更高），不是宣传的 -83%。
- -83% 是相对 Claude/GPT 这类"小作文化"模型的量级。
- 绝对账单仍然漂亮：同任务量级下时均 ¥7.96 → ¥3.59（-55%）。

### 被复盘双方一致认定的核心价值

1. **正确率提升 > 省钱**。"证伪后再动手"让方案一把过的概率大增；省下的不是输出 token，是"部署 → 报错 → 粘回日志 → 重改"的返工循环——那才是无底洞。
2. **"自信力"规则最值钱**。砍掉 AI 质疑不存在问题的自我询问（"Wait, is the project actually do something like this?"），把质疑权从"脑补"收回到"文件系统"：要怀疑就必须读源码，读不到证据就闭嘴往前推。
3. 综合体感：等于雇了一个资深工程师连续干 4~5 小时的脑力活，账单不到一杯星巴克。

## 已知短板

这套规则不是免费的，以下场景慎用：

1. **牺牲可读性与容错**。"能用代码表达就绝不写文字"在复杂任务上是双刃剑：甩出一段无注释、无思路的代码，你很难判断逻辑是否踩坑；一旦写错，读代码 Debug 的时间成本远高于省下的 token。
2. **不适合探索性/创造性任务**。突破进展三问要求立即刹车换路，做架构设计、技术选型、未知 Bug 排查时过早刹车会扼杀备选方案，陷入局部最优——实测数据里工具耗时 +68% 已经暴露了这个倾向。
3. **样本量少**。n=1 / 单小时账单，-83% 和 -42% 都只是方向性证据；重上下文任务（连读 10 个文件）里"少读多做"会导致反复回头读，把省下的 token 转移成工具执行费。

一句话：**省钱规则适合交付型任务（改 Bug、写功能、跑流程），不适合想不清楚的任务。** 想不清楚时宁可说"少废话"关掉它。

上述短板已针对优化（v2 规则）：开头加**模式判断**（交付型/探索型分流，探索型豁免三问与少读）；回复加**一行注释/根因**条款（复杂逻辑必须说明意图）；原则加**一次读够**条款（宁多读一层，不回头重读）。
